# Grid Module — Descriptive Overview

> **Project:** Grid-Based Strategy Game  
> **Module:** 01 — Grid System  
> **Document type:** Module design explanation  
> **Status:** Draft for review

## Module purpose

The Grid Module creates and manages the battlefield on which every match takes place. It provides the shared spatial structure used by units, movement, attacks, deployment, selection and highlighting.

The battlefield is presented as a 3D arena, but its gameplay is controlled through a flat grid of square cells. The visual arena can eventually contain detailed floors, walls, banners and environmental decoration, but those elements do not decide where units can stand or how actions are resolved.

The Grid Module should feel dependable and almost invisible during play. Players should not need to understand its internal construction. They should simply see a clear battlefield where positions, distances and boundaries are consistent.

## What the Grid Module owns

The Grid Module owns:

- Logical grid coordinates.
- The active and inactive state of cells.
- Arena layout profiles.
- Grid-to-world and world-to-grid positioning.
- Spatial relationships between cells.
- Runtime cell occupancy.
- Deployment-zone information.
- Arena boundaries.
- Symmetrical arena authoring tools.
- Grid-specific validation and debugging tools.
- The Grid state required for resetting or restoring a match.

The Grid Module does not own:

- Unit statistics or abilities.
- Movement and attack rules.
- Player selection.
- Normal gameplay highlighting.
- Turn order or recovery.
- Army construction.
- Private formation editing.
- Ready states.
- Victory conditions.

The Grid provides spatial facts. Other Modules decide what those facts mean during play.

## Battlefield structure

Every arena begins with a rectangular backing grid that defines its maximum width and height. Not every coordinate inside that rectangle needs to be playable.

Individual coordinates may represent:

- Active gameplay cells.
- Inactive coordinates.
- Team A deployment cells.
- Team B deployment cells.
- Neutral No Man’s Land cells.

Inactive coordinates are treated as if they do not exist. They are not blocked terrain and should not appear as selectable, occupiable or interactive spaces.

This allows a rectangular backing grid to produce different arena silhouettes, including:

- Rectangles.
- Tapered battlefields.
- Cut-corner arenas.
- Octagonal arenas.
- Grid-approximated circles.
- Bespoke symmetrical shapes.

The underlying cells remain square regardless of the overall arena shape. A circular arena therefore has a stepped gameplay edge constructed from square cells, while its surrounding 3D floor or wall can appear smoothly circular.

The visual boundary must never change the logical boundary. A decorative wall may surround the Grid, but it cannot make an inactive coordinate playable or obstruct the centre of an active cell.

## Fair and symmetrical arenas

Every competitive arena must give both players identical battlefield geometry.

The playable shape uses 180-degree rotational symmetry. One player’s side is mirrored through the centre to create the opposing side. Deployment capacity, available space and distance from the centre should therefore be equal.

The arena is divided conceptually into three regions:

1. Team A’s deployment side.
2. Neutral No Man’s Land.
3. Team B’s deployment side.

Players may arrange units anywhere within their own deployment area before combat. Units cannot initially be deployed in No Man’s Land or the opposing deployment area.

Different approved Arena Profiles may exist, but both players in a match always use the same profile.

## Cell-centred positioning

Every logical Grid coordinate represents the **centre of a square cell**, never the corner or intersection between several cells.

A unit placed at coordinate `(x, z)` stands in the middle of that cell. Unit models, capsules, selection markers, deployment previews, highlights and effects should all use the centre position supplied by the Grid Module.

No other Module should apply its own half-cell correction.

### Arena centre and Grid root

The Grid root represents the centre of the complete arena.

Logical coordinates remain simple non-negative integers:

```text
(0, 0) to (width - 1, height - 1)
```

Coordinate `(0, 0)` is the first allocated cell; it does not need to be positioned at Unity world origin. The Grid Module positions every cell relative to the centred Grid root.

Conceptually, a cell centre is positioned using:

```text
Cell centre X = (x - (width  - 1) / 2) × cell size
Cell centre Z = (z - (height - 1) / 2) × cell size
```

The Unity Y axis represents height above the arena floor and is not part of the two-dimensional logical coordinate.

### Odd-sized arenas

An odd-sized arena has one central cell positioned directly on the Grid root.

For a 9×9 arena with a cell size of one Unity unit:

```text
Logical centre cell: (4, 4)
World position:       (0, 0, 0)

(0, 0) → (-4, 0, -4)
(8, 8) → ( 4, 0,  4)
```

### Even-sized arenas

An even-sized arena has no single central cell. The Grid root sits between the central four cells.

For a 10×10 arena with a cell size of one Unity unit:

```text
(4, 4) → (-0.5, 0, -0.5)
(5, 4) → ( 0.5, 0, -0.5)
(4, 5) → (-0.5, 0,  0.5)
(5, 5) → ( 0.5, 0,  0.5)
```

The cells are still positioned by their centres. Only the centre of the complete arena lies between cells.

This convention allows odd and even arena dimensions to preserve correct rotational symmetry without placing units on grid-line intersections.

### Objects using cell centres

The following should request their positions from the Grid Module:

- Unit capsules and final character models.
- Selection markers.
- Movement destinations.
- Deployment previews.
- Health and status displays anchored to units.
- Attack effects.
- Projectiles targeting cells.
- Cell highlights.
- Debug labels and overlays.

## Runtime behaviour

At the beginning of a match, the Grid Module loads the selected Arena Profile and constructs the logical battlefield.

It establishes:

- Which cells exist.
- Where each cell appears in the Unity world.
- Which cells are active.
- Which deployment zone each cell belongs to.
- Which cells are occupied.
- Where the arena boundary lies.

Other Modules use this information without recreating it.

For example:

- The Unit Module records which coordinate a unit occupies.
- The Action Module asks for nearby cells, lines and spatial relationships.
- The Selection & Details Module converts a pointer position into a coordinate.
- The Grid Highlighting Module displays cell collections supplied by other systems.
- The Match Setup Module uses deployment zones when preparing the armies.
- Match Runtime loads the selected Arena Profile and coordinates Grid lifecycle operations.

The Grid can report that a cell exists, is active and is unoccupied. It does not decide whether a particular unit has sufficient movement or permission to enter that cell. That decision belongs to the Action Module.

## Cell occupancy

The Grid Module keeps an authoritative record of which runtime entity occupies each cell.

For the first version:

- Every unit occupies one cell.
- One cell can contain no more than one unit.
- Units cannot occupy inactive coordinates.
- Units cannot occupy positions outside the arena.
- Failed placement or movement cannot partially change Grid state.
- Removing a defeated unit frees its cell.

The relationship must remain consistent in both directions: a cell identifies its occupant, and an occupant can be located on its cell.

Occupancy represents spatial presence only. Unit health, race, damage, abilities and recovery remain owned by their appropriate Modules.

## Spatial information

The Grid Module provides consistent spatial information for the rest of the game.

This includes:

- Adjacent cells.
- Cardinal directions.
- Diagonal directions.
- Lines extending across the arena.
- Rectangular regions.
- Groups of cells around a position.
- Arena boundaries.
- Grid and world positions.

Inactive coordinates stop spatial paths at the edge of the playable arena. A line cannot travel through an inactive section and re-enter the battlefield elsewhere.

The Grid reports the geometry. The Action Module decides how movement and attack patterns interpret that geometry.

## Coordinate and world-state separation

Unit positions and gameplay rules use logical coordinates rather than relying on the exact Transform position of a capsule or model.

The Unity representation is calculated from logical state.

This means:

- Visual movement cannot accidentally change authoritative gameplay state.
- Capsule placeholders can be replaced without rewriting Grid rules.
- The visual Grid can be destroyed and rebuilt from data.
- The arena can be moved or rotated through its Grid root.
- Saved matches can restore units to exact cells.
- Automated Grid tests can run without loading the 3D arena.

The logical Grid remains the authority while the Unity scene displays its state.

## Grid data structures

The Grid Module uses separate data structures for reusable configuration and live match state.

### Grid Coordinate

A Grid Coordinate identifies one position inside the rectangular backing grid.

It contains the horizontal and vertical logical position used by gameplay systems. It does not contain a Unity world position, unit statistics or visual information.

### Grid Cell

A Grid Cell represents one allocated coordinate and its current spatial state.

It may contain:

- Coordinate.
- Stable cell identity.
- Active or inactive state.
- Deployment-zone assignment.
- Current occupant reference.
- Relevant boundary information.

A Grid Cell should not contain movement distance, attack values or selection colours. Those responsibilities belong to other Modules.

### Arena Grid Profile

An Arena Grid Profile is a reusable ScriptableObject describing one approved battlefield layout.

Suggested asset type:

```text
ArenaGridProfile
```

It contains:

- Unique profile identity.
- Display name.
- Description.
- Schema version.
- Grid width and height.
- Cell size.
- Active-cell layout.
- No Man’s Land depth.
- Team A deployment area.
- Team B deployment area.
- Neutral cells.
- Active-cell count.
- Deployment capacity.
- Validation status.
- Deterministic layout checksum.
- Optional authoring notes.

The Arena Grid Profile is configuration data. It describes how a Grid should be created but does not contain the changing state of a live match.

It must not store:

- Current units.
- Current occupancy.
- Selected cells.
- Movement or attack highlights.
- Turn information.
- Pending private formations.
- Temporary debug state.

Multiple Arena Grid Profiles can be created and saved without changing runtime Grid code.

### Runtime Grid State

Runtime Grid State represents the live battlefield after an Arena Grid Profile has been loaded.

It contains information such as:

- Loaded profile identity.
- Created cells.
- Current occupancy.
- Runtime Grid status.
- Information required to reset or restore the Grid.

Runtime Grid State exists for the current match and remains separate from the reusable ScriptableObject.

### Grid Snapshot

A Grid Snapshot captures the logical state required to restore the Grid later.

It may record:

- Arena Grid Profile identity.
- Profile version.
- Layout checksum.
- Grid dimensions.
- Occupancy state.
- Snapshot schema version.

A snapshot should reference the Arena Grid Profile rather than duplicate the complete arena layout.

## Bespoke Arena Layout Editor

### Purpose

Custom arena layouts should not require manually editing arrays, typing coordinate lists or writing new code.

The Grid Module therefore includes a bespoke Unity Arena Layout Editor. This is a dedicated Editor window designed specifically for creating symmetrical battlefields for the game.

It should feel like a finished internal development tool rather than a temporary debug panel.

### Authoring workflow

The intended workflow is:

1. Create or select an Arena Grid Profile.
2. Choose the backing-grid dimensions.
3. Choose the depth of No Man’s Land.
4. Draw the playable shape on one player’s side.
5. See the opposing side generated automatically.
6. Edit the neutral centre.
7. Preview the complete battlefield.
8. Validate the layout.
9. Save it as a reusable ScriptableObject.

The developer normally edits only Team A’s side. The Editor generates Team B’s side through 180-degree rotation.

No Man’s Land has its own editing region. Neutral cells may be active or inactive, but they must preserve the arena’s symmetry and cannot become deployment cells.

### Editor presentation

The tool should use a spacious dedicated window rather than compressing the complete interface into a standard Inspector.

#### Profile and tools panel

- Selected profile.
- Create and duplicate actions.
- Grid dimensions.
- No Man’s Land depth.
- Drawing tools.
- Save and revert.
- Validation.
- Preview controls.

#### Grid canvas

- Large visual Grid.
- Pan and zoom.
- Active and inactive cells.
- Editable player side.
- Generated opposing side.
- Neutral territory.
- Coordinate labels.
- Mirror preview.
- Arena centre.

#### Properties and validation panel

- Profile summary.
- Active-cell count.
- Deployment capacity.
- Selected-cell information.
- Symmetry status.
- Connectivity status.
- Errors and warnings.

### Drawing tools

The Editor should provide clearly named tools such as:

- Activate Cells.
- Deactivate Cells.
- Paint Rectangle.
- Erase Rectangle.
- Fill Region.
- Clear Editable Side.
- Invert Editable Side.
- Apply Starting Preset.
- Preview Complete Arena.

The tool may provide starting presets such as rectangles, tapered arenas, octagons and grid-approximated circles. These are starting points and remain fully editable.

### Tool quality

Every control should have:

- A clear human-readable title.
- A helpful tooltip.
- Consistent spacing.
- An understandable disabled state.
- Confirmation before destructive changes.

The window should support:

- Undo and redo.
- Unsaved-change indication.
- Save, discard or cancel when closing.
- Zoom to fit.
- Reset view.
- Coordinate display.
- Scene focusing.
- Resizable panels.
- Scrollable areas where necessary.

The Editor should remain comfortable to use on a standard 1080p development display. It should not feel cramped or require the developer to understand internal field names.

### Layout validation

The Editor checks that an arena is suitable for gameplay.

Blocking problems include:

- Unequal player sides.
- Broken rotational symmetry.
- Disconnected battlefield regions.
- Isolated active cells.
- Empty deployment zones.
- Deployment cells inside No Man’s Land.
- No route connecting both sides.
- Invalid dimensions.
- Invalid centre handling.

Warnings may identify:

- Very small deployment areas.
- Narrow bottlenecks.
- Unusually large arenas.
- Excessive unused backing-grid space.
- Very short No Man’s Land.
- Layout changes made since the previous validation.

Validation messages should explain the problem, identify the affected area and suggest how it can be corrected.

An Arena Grid Profile should only become **Gameplay Ready** after passing every required validation.

## Debugging and diagnostics

The Grid Module includes dedicated debugging and diagnostic tools that expand alongside the Module.

These tools should be able to display:

- Coordinates.
- Cell identities.
- Cell centres.
- Active and inactive cells.
- Deployment zones.
- No Man’s Land.
- Occupancy.
- Arena boundaries.
- Spatial query results.
- Rays and regions.
- Profile identity.
- Profile version and checksum.
- Symmetry problems.
- Disconnected regions.
- Snapshot information.
- Initialisation and restoration failures.

Debug overlays should have individual visibility controls so the Scene view does not become cluttered.

Debugging tools read and display authoritative Grid information. They must not maintain an alternative version of the Grid or change gameplay behaviour simply by being enabled.

Editor-only tools must not be included in release builds. Runtime debug overlays should be disabled by default.

## Expected player experience

The Grid should make the battlefield immediately readable.

Players should be able to understand:

- Which spaces exist.
- Where units can stand.
- Where each army begins.
- Where neutral territory starts.
- Where the battlefield ends.
- How positions relate to one another.

The Grid itself should not draw attention away from the units and their actions. It provides a stable tactical surface that makes positioning, movement and attacks easy to understand.

## Module completion outcome

The Grid Module is complete when the project can:

- Load a reusable Arena Grid Profile.
- Construct its logical battlefield.
- Display that battlefield in Unity.
- Position every unit at the centre of its cell.
- Support odd and even arena dimensions correctly.
- Support custom symmetrical arena shapes.
- Convert reliably between Grid and world positions.
- Track cell occupancy.
- Provide consistent spatial information.
- Identify deployment and neutral zones.
- Place both armies atomically.
- Reset and restore runtime Grid state.
- Explain invalid configurations clearly.
- Visualise authoritative state through development tools.
- Operate independently of Units, Actions, Turns, Selection and Highlighting.

The finished result is not merely a visible collection of squares. It is a reusable battlefield-authoring and spatial foundation on which every later gameplay Module can safely depend.
