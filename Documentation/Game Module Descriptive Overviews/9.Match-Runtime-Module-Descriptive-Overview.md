# Match Runtime Module — Descriptive Overview

> **Project:** Grid-Based Strategy Game  
> **Module:** 09 — Match Runtime System  
> **Document type:** Module design explanation  
> **Status:** Draft for review

## Module purpose

The Match Runtime Module coordinates the complete battle. It creates the match from validated setup data, connects the other Modules, receives player commands, observes authoritative results, checks victory and brings the match to a controlled conclusion.

It is the conductor of the system rather than a giant script containing every rule. Grid, Units, Actions, Turns and other Modules retain their own responsibilities.

## What the Module owns

Match Runtime owns:

- Match identity and lifecycle state.
- Match initialisation order.
- Connection of participating Modules.
- Creation of runtime units from setup data.
- Command routing.
- Coordination of authoritative results.
- Global match events.
- Victory-condition evaluation.
- Match completion.
- Reset, restart and shutdown.
- Match-level snapshots where required.
- Runtime diagnostics.

It does not own:

- Grid geometry.
- Unit statistics.
- Roster unlocks.
- Movement and attack calculations.
- Recovery timing.
- Player input presentation.
- Highlight rendering.
- Private army construction.

## Match lifecycle

The expected lifecycle is:

1. Receive a validated Match Setup result.
2. Select and load the Arena Profile.
3. Initialise the Grid.
4. Create runtime units from chosen Unit Definitions.
5. Commit both formations to the Grid.
6. Create or connect Unit Views and interface presentation.
7. Initialise Turn & Recovery state.
8. Begin combat.
9. Route player commands and coordinate results.
10. Evaluate victory after relevant changes.
11. End the match once.
12. Present the result and allow restart or exit.

Every stage should either complete successfully or return a controlled failure. The match should never enter combat with only part of its required state available.

## Match states

High-level runtime states may include:

- Not Initialised.
- Initialising.
- Awaiting Reveal.
- Starting Combat.
- In Progress.
- Resolving Action.
- Paused where supported.
- Ending.
- Completed.
- Failed.
- Resetting.

These describe the overall lifecycle and remain separate from the detailed activation phases owned by Turn & Recovery.

## Command routing

Selection, local input or a future AI submits player intent to Match Runtime.

Runtime determines the appropriate authoritative recipient and coordinates the result. For example, a movement request is evaluated by Turn state and Action rules, applied through Grid and Unit state, then exposed to presentation through events.

Runtime should not reproduce the Action Module's legality calculations. It ensures commands reach the right system in the right match state.

## Events and presentation

Global events may include:

- Match Initialised.
- Armies Revealed.
- Combat Started.
- Active Player Changed.
- Unit Moved.
- Unit Turned.
- Attack Resolved.
- Unit Damaged.
- Unit Defeated.
- Recovery Changed.
- Victory Detected.
- Match Ended.
- Match Reset.

Views, interface, audio and future animation systems listen to these events. They should not become the authority for whether the event occurred.

## Victory and match end

The first complete ruleset uses defeat of the opposing commander as its primary victory condition.

Match Runtime evaluates victory after relevant authoritative changes, such as a unit being defeated. It should support a clean victory-condition contract so later objectives can be introduced without embedding them into unrelated systems.

Match completion must be idempotent: repeated victory signals cannot end the same match several times or produce duplicate rewards and results.

Once the match enters Ending:

- New player actions are rejected.
- Pending logical resolution completes safely.
- Presentation may finish required sequences.
- The final result is recorded once.
- Restart and exit become available.

## Match data

Runtime match data may contain:

- Unique match ID.
- Match Rules reference.
- Arena Profile identity.
- Participating players and teams.
- Runtime unit collection.
- Overall match state.
- Turn State reference.
- Command and event sequence numbers.
- Victory-condition state.
- Final result.
- Match schema version.

Reusable rules and content remain referenced rather than copied unnecessarily.

## Snapshot and restoration

Where restoration is required, Match Runtime coordinates snapshots from the participating authoritative Modules.

A complete snapshot may include:

- Match identity and lifecycle state.
- Arena Profile and checksum.
- Grid occupancy.
- Runtime unit states.
- Turn and recovery state.
- Victory-condition state.
- Deterministic sequence information.

Runtime verifies that every component belongs to the same compatible snapshot before restoration. Partial restoration must fail safely.

## Failure handling

Initialisation and runtime failures should be explicit and diagnosable.

Examples include:

- Missing Arena Profile.
- Invalid army setup.
- Failed batch placement.
- Duplicate runtime unit identity.
- Incompatible snapshot.
- Command received in the wrong match state.
- Required Module unavailable.
- Victory result with no valid winner.

Runtime should stop safely, preserve diagnostic information and avoid leaving a partly interactive match.

## Bespoke Match Runner

A development Match Runner should make complete mechanical tests easy to launch.

It should support:

- Choosing Match Rules.
- Choosing an Arena Profile.
- Loading saved test armies and formations.
- Starting directly in setup, reveal or combat where valid.
- Restarting the match.
- Inspecting lifecycle state.
- Capturing and restoring snapshots.
- Simulating controlled failures.
- Viewing event history.
- Exporting a concise diagnostic report.

The runner should orchestrate normal Module entry points rather than creating a separate simplified version of the match.

## Debugging and diagnostics

Runtime diagnostics should display:

- Match ID and state.
- Initialisation stage.
- Connected Modules and versions.
- Arena Profile.
- Player and team identities.
- Runtime unit count.
- Active player and unit.
- Last commands and results.
- Event sequence.
- Victory-condition status.
- Snapshot status.
- Failure reason.

The event history should be filterable so developers can follow one unit, command category or Module without excessive noise.

## Expected player experience

The match should feel continuous even though several independent Modules cooperate underneath it. Setup should transition cleanly into reveal, reveal into combat, and combat into a single understandable result.

Players should not encounter partially started matches, duplicated actions, unexplained control loss or victory screens appearing more than once.

## Module completion outcome

The Match Runtime Module is complete when the project can:

- Create a match from validated setup data.
- Initialise every required Module in a safe order.
- Create runtime units and reveal formations.
- Begin and coordinate combat.
- Route player intent without duplicating Module rules.
- Publish consistent match events.
- Detect commander defeat and end the match once.
- Reject commands after completion.
- Reset and restart cleanly.
- Coordinate compatible snapshots where required.
- Report failures and lifecycle state clearly.
- Run the complete capsule-based local match from setup to result.

The finished Match Runtime Module turns the independent systems into one reliable playable match while preserving the boundaries that keep the project maintainable.
