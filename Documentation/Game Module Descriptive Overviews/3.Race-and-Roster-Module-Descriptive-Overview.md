# Race & Roster Module — Descriptive Overview

> **Project:** Grid-Based Strategy Game  
> **Module:** 03 — Race & Roster System  
> **Document type:** Module design explanation  
> **Status:** Draft for review

## Module purpose

The Race & Roster Module organises Unit Definitions into playable fantasy races and controls which units become available as each race is developed or levelled.

Its purpose is to give armies a strong identity without forcing players to relearn the entire game for every race. Familiar battlefield roles create a shared language, while race-specific behaviour, advanced classes and signature units create variety.

Initial race ideas include Humans, Orcs and Undead, with room for branches or future races involving Vampires, Werewolves and Witchcraft.

## What the Race & Roster Module owns

The Module owns:

- Race definitions.
- Membership of units within a race roster.
- Race progression levels.
- Unit unlock requirements.
- Starter roster requirements.
- Advanced and signature-class availability.
- Race identity descriptions and tags.
- Roster validation.
- Race-specific content diagnostics.

It does not own:

- Unit combat statistics themselves.
- Army points and capacity validation for a match.
- Runtime unit state.
- Actions or abilities in battle.
- Matchmaking or player accounts.
- Deployment.
- How experience is awarded after a match.

The Module describes what belongs to a race and what is available. Match Setup decides what the player can take into a particular battle.

## Race definitions

Each race should be represented by a reusable ScriptableObject.

Suggested asset type:

```text
RaceDefinition
```

A Race Definition may contain:

- Stable race ID.
- Display name and description.
- Player-facing identity summary.
- Visual and audio theme references.
- Race tags.
- Maximum progression level.
- Starter unit references.
- Full roster entries.
- Unlock structure.
- Signature-class references.
- Content version.
- Balance and authoring notes.

The Race Definition does not copy Unit Definition data. It references the units that belong to its roster.

## Starter roster

Every race begins with three accessible battlefield roles:

- A durable tank or frontliner.
- A ranged unit.
- An inexpensive pawn-style unit.

These roles ensure that a newly available race can immediately form a functional small army.

Starter units should remain useful after advanced classes unlock. Progression should increase strategic options rather than simply replace early units with stronger versions. Points, capacity, recovery and specialised roles can keep inexpensive units relevant.

## Shared and race-specific roles

Races may share recognisable archetypes such as:

- Warrior.
- Archer.
- Mage.
- Tank.
- Support.
- Fast attacker.

The exact unit should still express its race. A Human frontline unit, Orc frontline unit and Undead frontline unit may occupy similar army roles while behaving or presenting themselves differently.

Advanced units provide stronger identity, such as:

- Human Paladins.
- Undead Necromancers.
- Orc Shamans.
- Vampire elites.
- Werewolf assault units.
- Witchcraft-based support or control units.

A mature race can culminate in one or two signature classes. These should be distinctive strategic options rather than automatic replacements for every cheaper unit.

## Race progression and unlocks

Race progression controls access to roster options.

The expected experience is:

1. The player begins with the three starter roles.
2. Playing or progressing with that race increases its level.
3. New units or branches become available at defined milestones.
4. Advanced classes widen possible army compositions.
5. Signature classes become long-term roster goals.

The Race & Roster Module stores the unlock requirements and can report what should be available for a given race level. A separate progression or profile system may eventually store the player's actual earned experience.

## Roster entries

A roster entry connects a Unit Definition to its place inside a race.

It may describe:

- Unit Definition reference.
- Unlock level.
- Starter status.
- Shared, advanced or signature classification.
- Prerequisite branch or unit.
- Roster category.
- Maximum availability where needed.
- Display ordering.
- Unlock description.

The entry should not duplicate combat statistics such as health or damage.

## Army-building relationship

The Race & Roster Module answers questions such as:

- Does this unit belong to the selected race?
- Is it unlocked at this race level?
- Is it a starter, advanced or signature option?
- Which units should appear in the roster browser?

Match Setup answers different questions:

- Can the player afford this unit with the remaining points?
- Does the army have enough capacity?
- Has the maximum team size been reached?
- Is the final army valid for this match?

Keeping these responsibilities separate allows roster progression to change without rewriting army construction.

## Bespoke Race and Roster Editor

The project should provide a dedicated editor for building and reviewing race rosters.

The tool should include:

- Searchable race list.
- Race identity and description panel.
- Starter-roster section.
- Level-based unlock timeline.
- Drag-and-drop roster ordering.
- Unit-role filters.
- Signature-class section.
- Missing-reference warnings.
- Duplicate-entry detection.
- Unlock-path validation.
- Preview at a selected race level.
- Comparison between two races.
- Clear titles, tooltips and spacious panels.

The level preview should show exactly which units would be available at a chosen progression level. This allows the roster to be reviewed from the player's perspective without changing saved progression data.

## Validation

A race should not be considered ready if:

- It has no stable identity.
- It lacks any of the three starter roles.
- A roster entry references a missing Unit Definition.
- Two entries conflict or duplicate one another unintentionally.
- An unlock requires an impossible prerequisite.
- A signature class has no valid unlock point.
- Display ordering is ambiguous.
- A referenced unit is not permitted for that race.

Warnings may identify weak role coverage, too many units unlocking at once or starter units that appear to become redundant.

## Debugging and diagnostics

Diagnostics should display:

- Selected race and version.
- Current test level.
- Available and locked units.
- Unlock reasons.
- Missing prerequisites.
- Starter-role coverage.
- Advanced and signature classifications.
- Duplicate or unreachable entries.
- Unit-definition references.

The developer should be able to choose a test level and inspect the resulting roster without altering player progression.

## Expected player experience

Choosing a race should immediately communicate a tactical identity and future direction. A new player should receive enough familiar roles to build a sensible army, while continued progression reveals more specialised ways to play.

Unlocking a new class should create a strategic possibility rather than a compulsory upgrade. Earlier units remain meaningful because army points, capacity, recovery and battlefield role still matter.

## Module completion outcome

The Race & Roster Module is complete when the project can:

- Create reusable Race Definition assets.
- Assign Unit Definitions to race rosters.
- Guarantee the required starter roles.
- Describe level-based unit unlocks.
- Represent advanced branches and signature classes.
- Report available and locked units for a given level.
- Validate roster completeness and unlock paths.
- Preview and compare races through a bespoke editor.
- Expose roster diagnostics.
- Supply valid availability information to Match Setup without owning army construction.

The finished Module provides the content structure through which the game's collection of units becomes a set of understandable, expandable fantasy armies.
