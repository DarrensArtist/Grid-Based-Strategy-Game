# Selection & Details Module — Descriptive Overview

> **Project:** Grid-Based Strategy Game  
> **Module:** 06 — Selection & Details System  
> **Document type:** Module design explanation  
> **Status:** Draft for review

## Module purpose

The Selection & Details Module translates player input into clear tactical intent and presents the information needed to make a decision.

It handles hovering, selecting cells and units, choosing available actions, cancelling choices and inspecting unit details. It is the player's main conversational layer with the match, but it does not decide whether an action is legal or directly alter authoritative state.

## What the Module owns

The Module owns:

- Pointer and selection interpretation.
- Hovered cell and unit.
- Selected cell and unit.
- Current player-facing choice.
- Action-menu presentation.
- Unit and cell detail panels.
- Cancel, back and confirmation interaction.
- Input-mode transitions.
- Selection-specific feedback and diagnostics.

It does not own:

- Grid coordinate conversion rules.
- Unit state.
- Action legality.
- Highlight calculation.
- Turn progression.
- Damage or movement resolution.
- Army construction rules.
- Match victory.

## Hovering and inspection

When the player points at the arena, the Grid Module determines whether the pointer corresponds to an active coordinate. Selection uses that result to identify the relevant cell and occupant.

Hovering may show lightweight information such as:

- Coordinate.
- Occupant name.
- Team.
- Health.
- Recovery.
- Facing.
- Basic threat or action preview where another Module supplies it.

Hovering should never alter match state.

## Selecting a unit

A normal combat selection flow should feel direct:

1. The player points at a friendly ready unit.
2. The unit receives a clear selection treatment.
3. Its important details appear.
4. Available action categories are shown.
5. The appropriate Module supplies legal choices.
6. The player chooses, confirms or cancels.

If a unit is not selectable, the interface should explain the reason where useful—for example, wrong team, still recovering or already defeated.

Selection state is temporary interface state. It must be cleared or updated when the selected unit is defeated, the phase changes or control passes to the opponent.

## Player intent

Selection produces requests such as:

- Select this unit.
- Inspect this cell.
- Begin movement choice.
- Attempt movement to this coordinate.
- Choose this facing.
- Begin attack choice.
- Attempt attack on this target.
- Wait.
- Cancel current choice.

It submits these requests to Match Runtime or the relevant authoritative system. It does not move a capsule, change facing or reduce health directly.

## Details presentation

The unit details panel should prioritise information required for the current decision.

Core information may include:

- Unit name and role.
- Race.
- Team.
- Current and maximum health.
- Current recovery.
- Facing.
- Movement description.
- Attack description.
- Damage or action summary.
- Army point and capacity cost during setup.
- Relevant status effects when introduced.

The panel should avoid presenting every internal number at once. Advanced information may be revealed through expanded sections or tooltips.

## Input methods

The Module should be designed around actions rather than one specific device. Mouse and keyboard may be the first implementation, but selection concepts should remain suitable for controller or touch later.

Input prompts and focus behaviour should adapt to the current input method without changing authoritative match rules.

## Interface state

Runtime selection state may contain:

- Hovered coordinate.
- Hovered runtime unit ID.
- Selected coordinate.
- Selected runtime unit ID.
- Current choice mode.
- Pending destination or target.
- Focused interface control.
- Last rejection message.

This state should not be included in authoritative replays or saved matches unless a specific resume experience requires it.

## Bespoke UI presentation tools

The project should provide reusable UI components and preview tools for unit details rather than constructing each panel manually.

A development preview should allow:

- Loading any Unit Definition.
- Supplying example runtime values.
- Previewing healthy, wounded, recovering and defeated states.
- Testing long names and descriptions.
- Testing missing portraits or placeholder models.
- Previewing different resolutions and interface scales.
- Checking mouse, controller and keyboard focus.
- Reviewing tooltips and expanded information.

The tool should make clipped text, missing labels and inaccessible controls obvious.

## Feedback and error handling

Rejected intent should produce specific feedback without overwhelming the player.

Examples include:

- This unit is still recovering.
- This unit belongs to the opponent.
- That cell is outside the battlefield.
- The destination is no longer available.
- No valid target occupies that cell.
- The current activation phase does not allow this action.

The authoritative Module supplies the rejection reason. Selection decides how to present it.

## Debugging and diagnostics

Diagnostics should show:

- Current input method.
- Pointer world position.
- Resolved Grid coordinate.
- Hovered cell and unit.
- Selected cell and unit.
- Current choice mode.
- Available action categories.
- Pending request.
- Last accepted or rejected command.
- Current UI focus.
- Reason selection was cleared.

Development overlays may identify pointer hits and selection transitions, but normal gameplay visuals belong to Grid Highlighting and Unit Views.

## Expected player experience

Selection should feel immediate, calm and predictable. The player should never wonder which unit is selected, what information is relevant or how to return to the previous choice.

The interface should help the player understand the battlefield without playing the game for them. It presents facts, valid options and consequences clearly while leaving tactical decisions to the player.

## Module completion outcome

The Selection & Details Module is complete when the project can:

- Hover and inspect active cells and units.
- Select only appropriate units for the current context.
- Present readable unit and action information.
- Guide the player through movement, facing, attack and waiting choices.
- Submit intent without directly changing match state.
- Cancel and back out consistently.
- Clear invalid selection after state changes.
- Explain rejected choices.
- Support accessible focus and scalable UI presentation.
- Expose selection diagnostics.

The finished Module gives the player a reliable way to understand and operate the tactical systems without duplicating their underlying rules.
