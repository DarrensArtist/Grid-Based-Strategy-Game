# Unit Module — Descriptive Overview

> **Project:** Grid-Based Strategy Game  
> **Module:** 02 — Unit System  
> **Document type:** Module design explanation  
> **Status:** Draft for review

## Module purpose

The Unit Module defines what a unit is and represents every individual combatant taking part in a match. It provides the shared unit information used by army construction, deployment, actions, recovery, selection and match results.

The system must separate a reusable unit type from the changing state of a particular unit in battle. Two Swordsmen may share the same definition while having different health, positions, facing and recovery during the match.

The first version uses coloured capsules, but the Unit Module must already behave as though those capsules are complete characters. Replacing a capsule with a model and animation controller should not change the unit's identity or combat data.

## What the Unit Module owns

The Unit Module owns:

- Reusable unit definitions.
- Unique runtime unit identities.
- Team ownership.
- Current health and alive state.
- Current facing.
- Current recovery value.
- Reference to the unit's current Grid coordinate.
- Unit tags and classifications.
- Presentation references for capsules and future models.
- Unit-specific validation and diagnostics.

It does not own:

- Which units a race unlocks.
- Army points and capacity validation.
- Whether a movement or attack is legal.
- Damage calculation and action resolution.
- Turn progression.
- Grid occupancy.
- Player input and selection.
- Match victory conditions.

## Unit definitions

A Unit Definition describes one reusable type of combatant. It should be represented by a ScriptableObject so units can be created and balanced as content rather than hard-coded into match logic.

Suggested asset type:

```text
UnitDefinition
```

A definition may contain:

- Stable definition ID.
- Display name and description.
- Unit role.
- Army point cost.
- Team-capacity cost.
- Maximum health.
- Base recovery value.
- Movement-pattern reference.
- Attack-pattern reference.
- Base damage or action references.
- Allowed facing behaviour.
- Unit tags.
- Race or roster compatibility references.
- Capsule colour and placeholder presentation.
- Future model, portrait and animation references.
- Content version and balancing notes.

The Unit Definition describes the starting rules for that unit type. It does not store the health, position or recovery of a unit currently in a match.

## Runtime units

A Runtime Unit represents one individual instance created for a match.

It may contain:

- Unique runtime ID.
- Unit Definition reference.
- Team or player ID.
- Grid coordinate.
- Current health.
- Current facing.
- Current recovery.
- Alive, defeated or removed state.
- Runtime status-effect references when that feature is introduced.
- Match-specific modifiers.

Runtime identities must remain stable for the complete match. Other systems should refer to the runtime ID rather than relying on a GameObject name or scene reference.

## Health and defeat

The Unit Module stores a unit's health and defeated state, while the Action Module determines when and why damage is applied.

Expected behaviour includes:

- Health cannot exceed the unit's permitted maximum without an explicit effect.
- Damage cannot make health ambiguous or leave a unit partly defeated.
- Reaching the defeat threshold produces one clear state transition.
- A defeated unit can no longer be treated as ready or selectable for normal actions.
- Grid occupancy is released through the correct cross-Module flow.
- Repeated defeat requests cannot create duplicate removal results.

The visual disappearance, death animation or capsule effect presents the result; it does not define whether the unit is alive.

## Facing

Units can face one of the eight directions supported by the Grid. Facing is stored as part of Runtime Unit state because attacks, defences and later abilities may depend on orientation.

The Unit Module records the current direction. The Action Module decides whether changing direction is legal, when it may happen and whether it consumes an action.

A clear visual arrow or capsule marker should display facing during the prototype. Future character models can replace that marker with visible model rotation.

## Recovery

Current recovery belongs to the Runtime Unit because it is a changing property of that individual combatant.

The Unit Module stores the value, but the Turn & Recovery Module controls:

- When recovery is assigned.
- When it counts down.
- When the unit becomes ready.
- What happens if no unit is ready.

This separation allows the same unit state to be inspected without allowing the Unit Module to advance the match independently.

## Unit presentation

The first presentation should communicate identity and state using simple capsules.

A prototype Unit View may show:

- Team colour.
- Unit name.
- Health bar.
- Recovery number.
- Facing arrow.
- Selection outline.
- Ready or unavailable state.
- Damage response.
- Defeat response.

The Unit View reads runtime state and presents it. Moving, rotating or deleting the view must not independently alter authoritative state.

## Bespoke Unit Definition Editor

Unit content will grow across several races, so definitions should be created through a clear bespoke editor rather than a cramped raw Inspector.

The tool should provide:

- Searchable unit list.
- Create and duplicate actions.
- Identity and naming section.
- Army-building values.
- Health and recovery section.
- Movement and attack references.
- Tags and race compatibility.
- Placeholder and final presentation references.
- Validation summary.
- Comparison with another unit.
- Unsaved-change indication.
- Clear titles and tooltips.

The editor should make dangerous omissions obvious, such as missing IDs, invalid costs, absent action references or duplicate definitions.

It should support reviewing related units side by side so later content can be balanced without repeatedly opening separate assets.

## Debugging and diagnostics

Unit diagnostics should be able to display:

- Runtime unit ID.
- Definition ID and version.
- Team ownership.
- Grid coordinate.
- Current and maximum health.
- Facing.
- Recovery.
- Alive or defeated state.
- Applied runtime modifiers.
- Missing references.
- Last state change.

Development controls may spawn test units, apply test damage, change facing or adjust recovery, but those controls must submit normal state-change requests rather than secretly editing an alternative state.

Editor-only tools must remain outside release builds, and runtime debug panels should be disabled by default.

## Expected player experience

Every unit should be easy to identify and understand. The player should be able to recognise what a unit is, which team it belongs to, how healthy it is, which direction it faces and whether it is ready to act.

Units should feel persistent and individual even when several share the same definition. A wounded Swordsman recovering near the centre is a different battlefield entity from a fresh Swordsman protecting the rear.

## Module completion outcome

The Unit Module is complete when the project can:

- Create reusable Unit Definition assets.
- Validate and compare those definitions.
- Spawn multiple runtime instances from one definition.
- Give every runtime unit a stable identity.
- Track team, health, facing, recovery and position references.
- Represent defeated units unambiguously.
- Display unit state through capsules without making views authoritative.
- Save or snapshot the runtime data needed by Match Runtime.
- Expose clear diagnostics.
- Operate without owning actions, turns, roster unlocks or Grid occupancy.

The completed Unit Module becomes the authoritative description of every combatant, while leaving the rules governing what those combatants may do to the appropriate Modules.
