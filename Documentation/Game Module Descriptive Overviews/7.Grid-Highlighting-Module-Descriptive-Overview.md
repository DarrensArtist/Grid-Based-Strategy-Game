# Grid Highlighting Module — Descriptive Overview

> **Project:** Grid-Based Strategy Game  
> **Module:** 07 — Grid Highlighting System  
> **Document type:** Module design explanation  
> **Status:** Draft for review

## Module purpose

The Grid Highlighting Module communicates tactical information directly on the battlefield. It displays cells supplied by other Modules using a consistent visual language for movement, attacks, deployment, selection and areas of effect.

Highlighting is presentation only. It must never calculate where a unit can move or attack. The same authoritative result used to accept an action is supplied to the highlighting system for display.

## What the Module owns

The Module owns:

- Highlight presentation styles.
- Highlight layers and priority.
- Showing and clearing supplied cell collections.
- Hover and selection cell treatments.
- Movement, attack and deployment presentation.
- Area-of-effect previews.
- Highlight animation and accessibility options.
- Highlight-specific diagnostics.

It does not own:

- Grid geometry.
- Movement or attack calculations.
- Target validation.
- Selection state.
- Unit state.
- Turn progression.
- Action resolution.

## Visual language

The initial game should use a small, consistent set of meanings.

Possible categories include:

- Selected cell.
- Hovered cell.
- Valid movement.
- Valid attack target.
- Attack pattern or threatened area.
- Area of effect.
- Friendly deployment.
- Opposing deployment.
- No Man’s Land.
- Invalid or blocked choice.
- Planned path.

Exact colours can change during presentation design, but the meanings must remain stable and distinguishable.

Colour should not be the only signal. Borders, icons, patterns, brightness and animation may reinforce meaning for colour-blind players.

## Highlight requests

Other Modules submit presentation requests containing:

- Highlight category.
- Cell collection.
- Owner or source where relevant.
- Priority.
- Optional duration.
- Optional style override.
- Context identifier used when clearing or replacing it.

The Grid Highlighting Module does not reinterpret the supplied cells. If an invalid or inactive coordinate is received, it should reject or report it rather than silently inventing a replacement.

## Layering and priority

Several meanings may apply to one cell at the same time. The Module requires a clear priority system so the result does not become a confusing blend.

For example:

- Hover should remain visible over a movement highlight.
- A selected target should be clearer than the wider attack area.
- An invalid state should not be hidden beneath a decorative pulse.
- Deployment zones should recede when a specific placement preview is active.

Layers should be composable without requiring other Modules to know material or rendering details.

## Highlight lifecycle

Highlights should appear and disappear according to their context.

Examples include:

- Movement cells appear when movement choice begins.
- They clear after moving, cancelling or changing phase.
- Attack cells replace movement information when attack choice begins.
- Deployment information appears during Match Setup.
- Hover follows the current pointer position.
- Match-end state clears tactical highlights.

Contexts should be cleared explicitly so stale information cannot remain after the authoritative state has changed.

## Presentation approach

The first implementation may use cell overlays, decals, simple meshes or material properties. The chosen approach should support:

- Large numbers of highlighted cells.
- Multiple visual categories.
- Smooth appearing and clearing.
- Grid-root movement and rotation.
- Different cell sizes.
- Custom active-cell arena shapes.
- Low visual clutter.

The underlying highlight request should remain independent of the final rendering technique.

## Highlight Style assets

Presentation styles may be represented through reusable assets.

Suggested asset type:

```text
GridHighlightStyle
```

A style may contain:

- Stable style ID.
- Display category.
- Colour.
- Border or pattern.
- Icon reference.
- Material reference.
- Animation behaviour.
- Pulse speed and intensity.
- Priority.
- Accessibility alternative.

These assets configure presentation and do not contain legal-cell calculations.

## Bespoke Highlight Style Editor

A visual editor should allow styles to be reviewed on an example Grid.

The tool should provide:

- Style library.
- Create and duplicate actions.
- Example Grid preview.
- Single and overlapping highlight previews.
- Priority preview.
- Light and dark arena-floor previews.
- Colour-blindness simulation where practical.
- Animation preview.
- Performance preview with many cells.
- Clear labels and tooltips.

The developer should be able to identify two categories that are too similar before testing them in a full match.

## Accessibility and readability

Highlights should remain readable:

- Against different arena materials.
- At the intended camera distance.
- During animation and visual effects.
- For common forms of colour-vision deficiency.
- When several layers overlap.

The game should allow excessive animation or pulsing to be reduced. Important information must remain visible when animation is disabled.

## Debugging and diagnostics

Diagnostics should display:

- Active highlight contexts.
- Cells in each context.
- Source Module.
- Style and priority.
- Overlapping layers.
- Rejected inactive coordinates.
- Last clear request.
- Current pool or renderer usage.
- Highlight counts.

A development mode may label each highlighted cell with its active categories and final chosen presentation.

## Expected player experience

The player should understand the board at a glance. When a unit is selected, legal destinations and targets should feel obvious without making the arena look excessively bright or busy.

The system should communicate possibility, danger and confirmation while allowing the units and arena to remain visually important.

## Module completion outcome

The Grid Highlighting Module is complete when the project can:

- Display supplied cell collections without calculating them.
- Present movement, attacks, deployment, hover and selection consistently.
- Handle overlapping meanings through clear priority.
- Clear stale contexts reliably.
- Support custom arena profiles and Grid-root transforms.
- Remain readable across supported arena materials.
- Provide accessible alternatives to colour-only communication.
- Author and preview reusable styles.
- Expose diagnostics for every active highlight.

The completed Module becomes the shared visual vocabulary through which every tactical system explains the Grid to the player.
