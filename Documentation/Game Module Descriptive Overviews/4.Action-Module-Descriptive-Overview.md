# Action Module — Descriptive Overview

> **Project:** Grid-Based Strategy Game  
> **Module:** 04 — Action System  
> **Document type:** Module design explanation  
> **Status:** Draft for review

## Module purpose

The Action Module defines what units can do on the battlefield and resolves the results of those actions. It brings movement, facing, attacks, damage and later abilities together under one consistent action process.

Its most important responsibility is to ensure that the cells shown as legal, the command accepted from the player and the result applied to the match all come from the same rules. Presentation systems may display legal choices, but they must not reproduce or reinterpret the rules independently.

## What the Action Module owns

The Action Module owns:

- Action definitions and categories.
- Movement-pattern interpretation.
- Attack-pattern interpretation.
- Facing-change rules.
- Legal-action queries.
- Target validation.
- Action resolution.
- Damage and effect requests.
- Action results and events.
- Action-specific validation and diagnostics.

It does not own:

- Grid geometry or occupancy records.
- Unit Definition content.
- Which race unlocks a unit.
- Turn progression or recovery countdowns.
- Player input.
- Visual highlights.
- Animation timing as gameplay authority.
- Match victory conditions.

## Action categories

The initial action language should include:

- Move.
- Change facing.
- Attack.
- Wait or end activation.

Later units may add actions involving:

- Push and pull.
- Leap or teleport.
- Healing.
- Area attacks.
- Lines and cones.
- Status effects.
- Friendly fire.
- Defensive stances.
- Race or class abilities.

These should extend the shared action framework instead of becoming isolated one-off scripts.

## Movement

Movement is based on the unit's movement pattern and the current Grid state.

The expected first flow is:

1. A ready unit is selected.
2. The Action Module reports its legal destinations.
3. Grid Highlighting displays those destinations.
4. The player chooses one destination or remains in place.
5. The destination is checked again against current authoritative state.
6. The logical move is resolved.
7. Presentation animates the unit between cell centres.

The Grid reports which cells exist and which are occupied. The Action Module decides whether a movement pattern can reach them and how intervening occupancy affects the path.

The initial rules should allow moving before attacking, but not attacking and then moving, unless a future unit or ability explicitly changes that sequence.

## Facing

Facing gives directional meaning to positioning.

The Action Module determines:

- Which directions may be chosen.
- When facing may change.
- Whether movement changes facing automatically.
- Whether a separate facing choice is required.
- Which attacks depend on orientation.

The Unit Module stores the resulting direction. The Unit View displays it.

## Attacks

An attack uses a reusable pattern to describe threatened or targetable cells.

Common pattern concepts include:

- Adjacent step.
- Cardinal or diagonal ray.
- Fixed offset.
- Leap.
- Line.
- Area around a target.
- Directional cone or arc.

Movement and attack patterns must remain independent. A unit may move like one chess piece and attack like another.

The Action Module must distinguish between:

- Cells in the attack pattern.
- Cells that are currently legal targets.
- Cells affected after a target is selected.
- Units actually damaged or otherwise affected.

## Deterministic resolution

The first version should use deterministic results. If an action is legal and its inputs are the same, it should produce the same logical result.

Visual timing, animation length and particle effects must not change damage, targets or occupancy. Presentation follows the resolved result and reports when it has finished displaying it.

Action results should clearly describe what happened, including:

- Acting unit.
- Action used.
- Start and destination cells.
- Chosen facing.
- Target cells or units.
- Damage or healing applied.
- Units defeated.
- Occupancy changes.
- Recovery recommendation.
- Failure reason when rejected.

## Action and pattern data

Reusable action content should be data-driven where practical.

Possible assets include:

```text
ActionDefinition
MovementPatternDefinition
AttackPatternDefinition
EffectDefinition
```

These assets describe player-facing and configurable behaviour, such as names, ranges, directions, target types and effect references. Runtime action requests and results remain match data rather than ScriptableObjects.

## Action requests

A player or AI expresses intent through an action request. The request identifies the acting unit, requested action and relevant choices.

The request does not directly move a GameObject or reduce health. The Action Module validates the request against current Grid, Unit and Turn state before producing an authoritative result.

Invalid requests should fail clearly without partially applying their effects.

## Bespoke Action and Pattern Editor

Because movement and attack patterns are central to roster variety, the project should provide a visual pattern editor.

The tool should allow a developer to:

- Create and duplicate definitions.
- Preview patterns around a centre cell.
- Enable cardinal and diagonal directions.
- Configure minimum and maximum range.
- Configure rays, leaps, lines and areas.
- Preview rotation through all facing directions.
- Add effect references.
- Inspect affected and targetable cells separately.
- Test the pattern against active boundaries and occupants.
- Compare two patterns.
- Validate missing or contradictory settings.

The preview should resemble the runtime Grid interpretation, not a separate artistic approximation. Controls should have clear titles and tooltips and should not be compressed into a raw Inspector.

## Debugging and diagnostics

Action diagnostics should display:

- Acting unit and action definition.
- Current activation phase.
- Candidate cells.
- Legal cells.
- Rejected cells and reasons.
- Selected path.
- Facing before and after.
- Target pattern.
- Affected area.
- Occupancy blockers.
- Damage and effect results.
- Last accepted or rejected request.

Scene overlays should visualise movement paths, rays, target areas and resolved effects without becoming the gameplay highlighting system.

## Expected player experience

Actions should feel readable and trustworthy. A player should be able to inspect a unit, understand the options shown, make a choice and see the expected result.

Power should come from pattern, positioning and timing rather than hidden uncertainty. When an action fails, the interface should be able to explain why.

## Module completion outcome

The Action Module is complete when the project can:

- Represent movement, facing, attacks and waiting through one action language.
- Query legal choices without changing match state.
- Validate a chosen action again before resolution.
- Move units through logical Grid coordinates.
- Resolve attacks, damage and defeat deterministically.
- Keep movement and attack patterns independent.
- Produce complete action results and events.
- Support visual pattern authoring and preview.
- Explain rejected actions clearly.
- Operate without owning input, highlights, turn progression or victory.

The finished Action Module becomes the authoritative bridge between player intent and changes to the tactical battlefield.
