# Turn & Recovery Module — Descriptive Overview

> **Project:** Grid-Based Strategy Game  
> **Module:** 05 — Turn & Recovery System  
> **Document type:** Module design explanation  
> **Status:** Draft for review

## Module purpose

The Turn & Recovery Module controls when players and units are allowed to act. It creates the tempo of the match by combining alternating player control with unit-specific recovery delays.

Players alternate taking one activation rather than moving an entire army at once. After a unit acts, it enters recovery and may be unavailable for several of its owner's later opportunities. Fast units can influence the battle frequently, while powerful units create longer openings after committing to an action.

## What the Module owns

The Turn & Recovery Module owns:

- Active player.
- Match-turn and activation counters.
- Activation phases.
- Unit readiness queries.
- Recovery assignment and countdown timing.
- Automatic passing.
- Activation completion.
- Control transfer between players.
- Turn-specific events and diagnostics.

It does not own:

- Unit base statistics.
- The actions a unit can perform.
- Grid occupancy.
- Player input.
- Unit selection presentation.
- Army setup.
- Damage or defeat resolution.
- Match victory conditions.

## Alternating activations

The expected combat rhythm is:

1. One player becomes active.
2. The player chooses one ready unit.
3. That unit completes its permitted activation sequence.
4. Recovery is applied.
5. The activation ends.
6. Control transfers to the opponent.

The system should never allow two units to be actively resolving actions at the same time.

## Activation phases

The initial match can use phases such as:

- Select Unit.
- Move.
- Choose Facing.
- Attack or Wait.
- Resolve.
- End Activation.
- Transfer Control.

Not every unit or action needs to use every visible choice, but the phase model must make it clear which kinds of command are currently acceptable.

The Action Module determines whether a specific movement or attack is legal. The Turn & Recovery Module determines whether that category of action is permitted at the current point in the activation.

## Recovery

Every runtime unit has a current recovery value. After acting, the value is set according to the unit and action result.

At the defined point in its owner's later turns, recovery counts down. Only units at zero are ready for normal activation.

Expected qualities include:

- Recovery changes are deterministic.
- The player can see when a unit will be ready.
- A unit cannot be selected merely because its view appears available.
- Powerful actions may recommend longer recovery than basic actions.
- Effects may later increase, decrease or pause recovery through explicit rules.

The Unit Module stores current recovery. This Module controls when and why it changes.

## Automatic passing

If the active player has no living ready unit, the system automatically passes control rather than waiting for an impossible input.

Automatic passing must be visible and explainable. It should not feel like the game skipped the player without reason.

The Module must also recognise conditions where repeated passing would continue indefinitely and allow Match Runtime to evaluate whether the match has stalled or ended.

## Activation commitment

Once a unit begins an activation, the system records its progress so the player cannot accidentally activate another unit midway through resolution.

The Module should know whether the active unit has:

- Been selected.
- Moved.
- Chosen facing.
- Attacked.
- Waited.
- Completed resolution.

This state governs sequence, not the spatial legality of the actions themselves.

## Turn state data

Runtime Turn State may contain:

- Active player ID.
- Activation number.
- Round or cycle number where required.
- Current phase.
- Active runtime unit ID.
- Completed activation steps.
- Pending control transfer.
- Automatic-pass count.
- Turn-state version.

Turn State is runtime data and should not be stored in a ScriptableObject.

Configurable rules, such as the initial phase sequence or recovery timing policy, may use a small Match Turn Rules asset if variation becomes necessary. The first version should avoid configurability that has no real use.

## Recovery preview and interface relationship

The Module should expose enough information for the interface to show:

- Which player is active.
- Which units are ready.
- Which units are recovering.
- Current recovery numbers.
- Expected recovery after a proposed action.
- Why a turn passed automatically.
- The current activation phase.

Selection & Details presents this information but does not decide readiness.

## Bespoke Turn Simulator

A development tool should allow the recovery rhythm to be inspected without playing a complete match.

The simulator should support:

- Creating a small list of test units.
- Assigning recovery values.
- Advancing activations.
- Applying action recovery.
- Showing ready and unavailable units.
- Demonstrating automatic passes.
- Displaying a recovery timeline.
- Resetting the scenario.
- Exporting clear diagnostic results.

The tool should use readable unit labels and a timeline rather than exposing only raw counters.

## Debugging and diagnostics

Diagnostics should display:

- Active player.
- Active unit.
- Current phase.
- Activation and round counters.
- Ready units by player.
- Recovery values.
- Last recovery changes.
- Last completed action.
- Automatic-pass reason.
- Pending transfer state.
- Invalid phase command reason.

Debug controls may advance or reset test state in development builds, but they must use the same authoritative transitions as normal play.

## Expected player experience

The player should always understand whose opportunity it is, which units can act and what will happen after committing a unit.

Recovery should create tactical anticipation rather than confusion. A heavy unit's powerful action should feel valuable, but the resulting delay should create a visible opportunity for the opponent.

## Module completion outcome

The Turn & Recovery Module is complete when the project can:

- Alternate one activation between players.
- Enforce a clear activation sequence.
- Identify ready and recovering units.
- Apply and count down recovery consistently.
- Prevent unavailable units from acting.
- Pass automatically when no unit is ready.
- Transfer control only after resolution completes.
- Expose clear state for the interface and debugging tools.
- Snapshot and restore turn state where required.
- Operate without calculating movement, attacks, damage or victory.

The completed Module provides the match's timing structure and makes recovery a central strategic resource rather than a hidden cooldown.
